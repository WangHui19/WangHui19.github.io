Flowable 工单全链路详解：核心表机制 + 监听器原理 + 真实投诉流程落地解析

前言

本文基于 JeecgBoot + Flowable 实际项目投诉工单业务，完整梳理：

  • Flowable 五大核心数据表分类及作用

  • act_ru_variable 与 act_hi_varinst 核心变量表区别

  • 执行监听器、任务监听器完整机制（start/end/take + 类/表达式/委托表达式）

  • 真实投诉工单全流程逐节点监听器、变量流转、数据落库逻辑

  • 工单从创建、流转、办结全链路数据生命周期

适合作为 Flowable 业务开发标准文档、新人培训文档、流程排障手册。

一、Flowable 五大核心数据表体系

Flowable 所有数据表严格分为 5 大类，理解分类即可看懂所有工单数据流转：

1. RE 资源定义表（act_re_*）——静态不变

存储流程部署、流程定义元数据，部署后基本不变化。

  • act_re_deployment：流程部署记录

  • act_re_procdef：流程定义（key、版本、bpmn 信息）

  • act_re_model：流程设计器模型数据

2. RU 运行时表（act_ru_*）——正在运行的工单

流程运行中存在，流程结束自动清空，待办列表全部来源于此。

  • act_ru_task：待办任务表（核心）

  • act_ru_execution：流程执行实例

  • act_ru_variable：运行时流程变量

  • act_ru_identitylink：任务候选人、办理人关联关系

3. HI 历史归档表（act_hi_*）——永久留存

流程结束后所有数据归档，用于查询历史工单、审批记录、变量追溯。

  • act_hi_procinst：历史流程实例

  • act_hi_taskinst：历史任务记录

  • act_hi_actinst：节点流转步骤记录

  • act_hi_varinst：历史变量快照表

  • act_hi_identitylink：历史审批人记录

4. GE 通用表（act_ge_*）

存储 BPMN 二进制、引擎配置属性。

  • act_ge_bytearray：BPMN 文件、流程图资源

  • act_ge_property：引擎版本与配置

5. ID 身份表（act_id_*）

Flowable 原生用户/角色表，Jeecg 项目基本不用，使用业务系统用户体系。

二、核心变量表深度区别（开发最容易混淆）

1. act_ru_variable（运行时变量）

  • 生命周期：流程运行期间存在，流程结束自动删除

  • 作用：节点判断、流程跳转、待办渲染、实时变量读取

  • 特点：全局变量/任务变量，实时覆盖更新

2. act_hi_varinst（历史变量快照）

  • 生命周期：永久归档，不会删除

  • 作用：追溯工单每一步状态变化、历史详情展示

  • 特点：变量每修改一次，生成一条快照记录

核心口诀：在办查 RU、办结查 HI、实时变量 RU、历史追溯 HI

三、Flowable 监听器完整机制（执行监听器 + 任务监听器）

1. 执行监听器 ExecutionListener（节点级）

作用于流程节点/流程实例，控制节点生命周期。

  • start：进入节点瞬间触发（初始化变量、前置校验）

  • end：节点执行完成、离开节点前触发（更新状态、发通知）

  • take：仅连线跳转触发，节点配置无效

2. 任务监听器 TaskListener（任务级）

只针对用户任务，控制待办任务生命周期。

  • create：任务创建

  • assignment：任务分配人变更

  • complete：任务审批完成（最常用）

  • delete：任务删除

3. 监听器三种实现方式对比

（1）类 Class

  • 填写全类名，Flowable 自动 new 对象执行

  • 无法注入 Spring Bean，@Autowired 为 null

  • 适用：简单日志、简单变量赋值

（2）表达式 Expression（项目最常用）

  • 直接编写 UEL 表达式，无需写类

  • 可操作 execution、task、可调用 Spring Bean 方法

  • 适用：单行变量赋值、简单业务逻辑

（3）委托表达式 DelegateExpression（正式业务推荐）

  • 填写 Spring Bean 名称 ${xxxBean}

  • Bean 托管于 Spring，支持依赖注入 Service/Mapper

  • 适用：更新业务表、发消息、复杂流程后置逻辑

四、真实业务：投诉工单全流程监听器拆解

工单流程链路：开始 → 投诉申请 → 工单受理及派单 → 投诉处理 → 满意度评价 → 结束

1. 节点一：投诉申请（用户制单节点）

执行监听器配置

  • start 表达式：${execution.setVariable('orderStatus','100')}

  • start 表达式：${execution.setVariable('orderStatus_dictText','制单')}

  • end 表达式：${execution.setVariable('orderStatus','0')}

  • end 表达式：${execution.setVariable('orderStatus_dictText','待分派')}

执行逻辑

  1. 进入节点：状态置为【制单】，用户正在填写投诉单

  2. 用户提交表单、节点结束：状态覆盖为【待分派】

数据落库

  • 运行时变量更新：act_ru_variable

  • 状态变更快照归档：act_hi_varinst

2. 节点二：工单受理及派单（客服操作节点）

执行监听器（end 事件，顺序执行）

  1. 表达式：临时设置状态文本为 已派单（用于消息文案）

  2. 类监听器：ActivityMessage2InitiatorListener —— 给投诉发起人推送【已派单】通知

  3. 表达式：设置状态码 orderStatus=1

  4. 表达式：最终覆盖状态文本为 待处理

任务监听器（complete）

  • ${execution.setVariable('archiveUser', task.getAssignee())}

  • 作用：记录本次受理派单的操作人ID存入流程全局变量

核心逻辑亮点

先临时赋值文案 → 发通知 → 再覆盖正式业务状态，实现「消息展示文案」与「业务状态字段」分离，是企业级流程标准写法。

数据落库

  • 更新 act_ru_variable 工单状态、归档人变量

  • 生成多条 act_hi_varinst 变更快照

  • 销毁当前任务 act_ru_task，归档任务记录 act_hi_taskinst

五、整体工单变量状态流转总览

  • 制单中：status = 100（制单）

  • 提交申请后：status = 0（待分派）

  • 受理派单完成后：status = 1（待处理）

  • 全程记录每一步操作人：archiveUser

六、常见生产问题与排障结论

  1. 业务表删除工单，待办依旧存在：Flowable 待办来自 act_ru_task，和业务表无关，需清理 RU 脏数据

  2. runtimeService 查询流程实例为 null：流程实例已销毁，只剩孤立任务，只能 SQL 清理 RU 表

  3. 变量历史记录不对：需查询 act_hi_varinst 快照，RU 表只存最新值

  4. 监听器 @Autowired 为空：Class 模式不支持 Spring 注入，必须改用委托表达式

七、总结

1. Flowable 工单本质就是：RU 表做实时流转、HI 表做永久追溯、监听器做业务联动。

2. 表达式适合简单变量赋值，委托表达式适合复杂业务回调，Class 模式仅适合轻量逻辑。

3. 本投诉流程通过多段监听器精准控制工单状态流转、消息通知、操作人记录，是一套标准的企业级 Flowable 业务流程落地方案。
